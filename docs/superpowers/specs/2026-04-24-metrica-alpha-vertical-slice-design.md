# Metrica Alpha 垂直切片设计

## 概述

这份文档只负责 Metrica 的第一条真实全链路 vertical slice。

它不重新解释双轨产品架构，也不重写 Runtime 协议字段或桌面工作台页面清单。  
它只回答一个问题：

> 第一条“可执行、可验证、可展示”的端到端链路具体是什么，以及它如何跨越 Core、Runtime、App 三层。

本阶段的 vertical slice 定义为：

**一个本地数据文件 -> 一个 OLS 模型配置 -> 一次真实拟合请求 -> 一份结构化结果 -> 一次桌面结果展示**

## 目标

这条 slice 的目标不是做出完整 Alpha，而是验证 5 个关键前提：

1. `MetricaBase.jl` 的结构化结果语义足以服务 Runtime 和 App。
2. `MetricaLinear.jl` 能以最小 OLS 实现承载第一条真实模型链路。
3. Runtime 能把拟合请求与结构化结果稳定搬运为协议对象。
4. App 能消费结果对象而不是解析终端文本。
5. 整条链路对“教学友好性”至少有最小体现，例如样本删除提示与可读错误。

## 用户故事

第一条 vertical slice 面向一个最小但真实的使用者：

> 用户打开桌面工作台，导入一个本地 CSV，输入一个 OLS 公式，点击运行，看到一份结构化结果摘要与系数表，并知道是否有缺失值导致样本变化。

这条故事必须成立，哪怕界面仍然简陋、模型仍然单一、导出能力仍然很轻。

## Slice 范围

### 包含

- 本地文件型数据输入，首批只要求 `CSV`
- 单一模型类型：`OLS`
- 单一主流程：拟合一次模型并展示结果
- 最小结构化结果：`glance`、`tidy`
- 最小消息与警告：样本删除信息、拟合失败错误
- Runtime 单次请求响应
- App 结果页真实渲染

### 不包含

- 多模型管理
- 面板、IV、GLS、WLS
- 完整 `augment` 大表渲染
- 诊断图系统
- 插件扩展机制的真实动态加载
- 云端、同步、多用户能力

## 各层职责

### Core

Core 在这条 slice 中必须提供：

- 一个可实例化的 OLS 模型定义对象
- 一个可序列化或可转换为协议对象的拟合结果
- 最小 `glance`
- 最小 `tidy`
- 至少一种警告对象，例如缺失值导致的删样提示

Core 在本阶段不需要：

- 完整统计推断家族
- 高级模型比较
- 丰富图形对象

### Runtime

Runtime 在这条 slice 中必须提供：

- 一个 `fit_model` 请求入口
- 从请求中解析数据引用和模型规范
- 调用 Julia 执行逻辑的固定桥接点
- 将结果转成稳定的成功响应
- 将错误转成稳定的错误响应

Runtime 在本阶段不需要：

- 常驻服务化
- 任务队列系统
- 分布式执行

### App

App 在这条 slice 中必须提供：

- 选择本地数据文件的入口
- 输入 OLS 公式的入口
- 触发一次拟合的动作
- 结果摘要卡片
- 系数表
- 消息与警告展示

App 在本阶段不需要：

- 全量项目系统
- 复杂多标签分析界面
- 高保真视觉系统

## 数据流

```mermaid
flowchart LR
    A["用户选择 CSV"] --> B["App 构造 fit_model 请求"]
    B --> C["Runtime 校验请求"]
    C --> D["Julia Core 读入数据并拟合 OLS"]
    D --> E["Core 返回结构化结果"]
    E --> F["Runtime 序列化成功/错误载荷"]
    F --> G["App 渲染 glance、tidy 与 warnings"]
```

这条链路里最关键的约束是：

- App 不解析 `summary()` 文本
- Runtime 不重做计量逻辑
- Core 不感知桌面布局

## 关键对象

### 输入对象

- `dataset_ref`
  - 指向本地 CSV 文件
- `model_spec`
  - 模型类型固定为 `ols`
  - 公式为字符串
- `options`
  - 至少支持缺失值默认删除策略

### 输出对象

- `glance`
  - 至少包含模型名、样本量、自由度、核心指标
- `tidy`
  - 至少包含参数名、估计值、标准误占位或真实值
- `messages`
  - 至少包含信息级和错误级消息
- `warnings`
  - 至少包含教学友好的可读解释对象

## 最小失败模式

这条 slice 至少要明确处理两个失败场景：

### 1. 数据问题

例如：

- 文件不存在
- CSV 无法解析
- 公式引用列不存在

要求：

- Runtime 返回稳定错误状态
- App 展示可读错误

### 2. 拟合问题

例如：

- 设计矩阵奇异
- 有效样本为空

要求：

- Core 产出明确错误语义
- Runtime 不吞掉错误原因
- App 不只显示“运行失败”，而要展示简要解释

## 教学友好性最低线

尽管这只是第一条技术链路，但它必须体现 Metrica 的教学定位。

最低要求：

- 若缺失值被删除，用户能知道删了多少行
- 若公式错误，用户能看到是哪个变量或项出错
- 若拟合失败，用户能看到简短原因和下一步建议

这部分不是视觉优化，而是协议和消息设计的一部分。

## 验收标准

当且仅当下面 6 条同时成立，这条 vertical slice 才算完成：

1. 存在一个真实可调用的 `fit_model` 入口。
2. 该入口能对一个本地 CSV 触发真实 OLS 执行。
3. 成功响应中包含结构化 `glance` 与 `tidy`。
4. 桌面端结果视图渲染这些结构化对象，而不是解析文本。
5. 至少一个缺失值或错误消息能端到端显示。
6. 整条链路可以被演示和复述为一个清晰故事。

## 后续设计衔接

一旦这条 slice 打通，后面的设计应按“在同一条链上加能力”推进，而不是再开平行但未打通的新链路。

优先追加顺序建议：

1. 让 `glance` 和 `tidy` 更完整
2. 让 Runtime 连接真实 Julia 进程
3. 让 App 从静态壳进入真实调用
4. 补最小导出能力
5. 再考虑 `augment`、HC1、更多教学解释

## 结论

Metrica 当前最重要的不是“再增加一个模块名字”，而是打通第一条可证明可运行的链路。

这份 vertical slice 设计的意义在于把项目从：

- 结构合理

推进到：

- 结构合理且链路成立

后续每一步实现都应以这条链路为主线，而不是偏离到新的未验证子系统中。
